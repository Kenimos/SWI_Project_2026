Parking Reservation System

A .NET 8 backend for managing parking areas, physical spots, and time-window reservations with local Driver and Approver roles.

Purpose and Users

Drivers

Find an available spot, create a reservation, confirm it, or cancel it before the start time.

Approvers

Review reservations that require approval and approve or reject them.

Operators

Maintain active parking spots and observe reservation state through the API.

Implemented Functionality

Reservations

OP-01 through OP-05 create, check, confirm, cancel, approve, reject, and expire reservations. Implemented and verified.

Authorization

Persisted Drivers and Approvers enforce creation, ownership, approval, and operator actions. Implemented and verified.

Parking areas

Approvers create areas and spots; area availability reports spot state and confirmed interval conflicts. Implemented and verified.

Physical state

Spots persist as FREE, RESERVED, OCCUPIED, or OUT_OF_SERVICE; check-in/check-out are available. Implemented and verified.

  |-- ParkingArea/ParkingSpot: area ownership and physical state
  |
  v
ParkingDbContext (EF Core) ---> SQLite

External Notification Service: documented boundary, not yet integrated

Important boundary: process-local locks protect the current single-instance baseline. A database-authoritative concurrency mechanism is required before multi-instance deployment.

Key Decisions

  • Reservation state is persisted as readable text through EF Core.
  • Time comparisons use UTC and an injectable clock.
  • Half-open intervals, [start, end), prevent false conflicts at touching boundaries.
  • Confirm and Cancel use the same spot lock; a stale Cancel is rejected if Confirm persisted first.
  • Approval expiry is evaluated lazily when a pending reservation is accessed.

Evidence and Verification

The project contains SQLite-backed xUnit tests for reservations, authorization, parking areas, physical spot states, approval, expiry, persistence, interval boundaries, concurrency, and HTTP endpoint contracts through WebApplicationFactory<Program>.

Verified result: full suite passed with 53 tests, 0 failures, and 0 skips using .NET SDK 8.0.132/runtime 8.0.32. The architecture ownership check also passed.

Known Gaps and Next Steps

  • Multi-instance reservation concurrency still requires a database-authoritative strategy.
  • Notification delivery and retry semantics are not implemented.
  • HTTP coverage currently focuses on representative endpoint contracts; broader endpoint and failure-matrix coverage can be expanded later.
  • External identity integration, frontend functionality, payment, and production scheduling remain out of scope.
